1. How to Use This Roadmap
This document is intended to be used as the build sequence for the complete system, not as a product pitch.
Every major module includes purpose, recommended technologies, concrete implementation tasks, data
contracts, test requirements, acceptance criteria, and dependencies. The order matters: the system must first be
able to reproduce the strategy deterministically and backtest it before a Decision Agent is allowed to issue live
recommendations.
Two types of content are deliberately separated throughout the document:
 SOURCE-DERIVED REQUIREMENT - based on the trading framework/course files you supplied. These
requirements preserve the framework terminology and are not silently replaced by generic trading advice.
 ENGINEERING RECOMMENDATION - a software architecture, technology, safety, or implementation decision
proposed to make the system reliable, testable, private, and maintainable.
The initial production system is a trading copilot. It may recommend ENTER_LONG, ENTER_SHORT, WAIT,
HOLD, REDUCE, TAKE_PARTIAL_PROFIT, EXIT, INVALIDATED, or NO_SETUP. Automatic money-moving
execution is not part of the initial release. An execution service is designed only as a future isolated extension.

2. Product Vision, Scope and Non-Goals
2.1 Product vision
Build a private, self-hosted, multi-market trading intelligence platform that continuously ingests Crypto and
Forex market data, understands the supplied trading framework, detects and validates setups, learns from
historical outcomes, explains its reasoning, and delivers clear decisions through a mobile application and
Telegram. The system should combine deterministic rule execution, statistical/ML decisioning, a private LLM,
multimodal screenshot analysis, RAG over trusted resources, backtesting, paper trading, journaling, and
analytics.

2.4 Non-goals for V1
 No autonomous live order placement.

 No model-generated risk values or confidence numbers without deterministic/statistical support.

9.2 Every ambiguous term becomes a versioned parameter or algorithm
Example: “significant volume increase” cannot remain English-only in the live engine. The implementation must
define one or more measurable candidate rules, test them on labeled examples, and store the selected rule under
a strategy version.
VolumeRule v1 candidate:
bos_volume_ratio = candle_volume / SMA(volume, 20)
significant_volume = bos_volume_ratio >= threshold
RetestVolumeRule v1 candidate:
retest_volume_ratio = retest_volume / SMA(volume, 20)
low_volume_retest = retest_volume_ratio <= threshold
The exact thresholds above are engineering placeholders until validated against the course examples and
historical data. They must not be presented as source-derived facts.

10. Decision Agent - Final Recommendation Brain
Figure 2. The Decision Agent is not a free-form LLM. It is a constrained decision pipeline. Hard rules and the Risk
Engine can veto a model prediction. The LLM explains and retrieves evidence; it does not invent the trading
math.
10.1 Decision pipeline
17. Build normalized MarketContext.
18. Generate deterministic features and strategy-rule outputs.
19. Apply hard no-trade gates (missing data, session/event restrictions, mandatory rule failure).
20. Score the candidate with a trained statistical/ML model.
21. Run the Risk Engine and exposure checks.
22. Calibrate probability/confidence using out-of-sample results.
23. Use the LLM to produce an explanation grounded in actual computed values and trusted course evidence.
24. Persist the full decision snapshot before notification.

10.2 Initial ML model
Start with LightGBM or XGBoost rather than training the main LLM. The first decision problem is tabular:
market structure, volume ratios, volatility, session, order-flow features, strategy conditions, risk values and
context. Tree boosting is easier to train, explain, calibrate and debug. More complex sequence models may be
evaluated later against the same holdout datasets.

10.5 Data leakage controls
 Feature timestamps must be <= decision timestamp.

 Never compute swing confirmation using candles that would not yet have existed at decision time unless the
strategy explicitly waits for confirmation and the confirmation latency is modeled.
 Use time-based train/validation/test splits, not random row splits.
 Keep entire contiguous market periods out-of-sample.
 Perform walk-forward testing before live paper deployment.
10.6 Confidence calibration
Model scores are not automatically probabilities. Calibrate on an untouched validation set (e.g., isotonic or Platt-
style calibration where appropriate), then monitor reliability diagrams. The LLM must never invent a
percentage. If calibration is weak, present qualitative confidence bands instead of fake precision.
10.7 Human feedback loop
Agent recommendation -> User action -> User reason -> Actual market outcome -> Review label -> Dataset version
User overrides are valuable training data but must not automatically become ground truth. They should be
reviewed or weighted based on outcome and rule adherence.

11. Logical Agent Design
Agent Responsibility
1. Orchestrator Routes questions/workflows; selects tools; never
computes trading values itself.
2. Knowledge Agent Retrieves approved course/strategy evidence and
surfaces conflicts or insufficient evidence.
3. Vision Agent Extracts chart-visible information; verifies
symbol/timeframe; never trusted alone for a trade.
4. Market Agent Primarily deterministic tools for live/historical market
data and feature queries.
5. Strategy Agent Explains Strategy Engine output and missing/failed
conditions; cannot bypass rules.
6. Risk Agent Explains deterministic Risk Engine result; can veto but
cannot loosen configured limits.
7. Signal Agent Formats setup lifecycle and notification state; does not
invent probability.
8. Journal/Analytics Agent Answers performance questions from computed
statistics and journal records.
9. Decision Agent Consumes validated features, ML score, risk result and
strategy state to issue the final recommendation state.

11.2 Structured LLM output requirement
Every agent-to-agent response must validate against a Pydantic model. Free-form prose is allowed only in the
final explanation field. If validation fails, retry with a constrained repair prompt; after the retry budget is
exhausted, fail closed and return a system error rather than guessing.

12.1 Why risk is separate
A good setup is not automatically an acceptable trade. Risk and portfolio limits are independent vetoes. This also
resolves differences between personal risk notes, course guidance, paper-trading policies and future account
sizes without editing strategy code.

12.3 Risk calculations
risk_per_unit = abs(entry - stop)
allowed_loss = min(account_balance * max_risk_pct, max_risk_amount_if_set)
quantity_raw = allowed_loss / risk_per_unit
quantity = normalize_to_lot_step(quantity_raw)
rr_to_target = abs(target - entry) / risk_per_unit
For Forex, pip value, quote currency conversion, contract size, spread and lot-step rules must be handled by an
instrument calculator. For crypto, exchange tick/step/min-notional rules must be validated.
13. Backtesting and Historical Research
13.1 Golden rule
The live Strategy Engine and the backtesting Strategy Engine must share the same core rule code. There must not
be one “backtest version” and a separate “live version” that drift apart.
13.2 Backtest simulation requirements
 Event-driven candle replay with strict timestamp ordering.
 Configurable fees, spread, slippage and minimum order constraints.
 No look-ahead bias in features, pivots, macro data or labels.

19.1 Database design rules
 Use UUID/ULID-style primary keys where globally unique IDs are helpful; use surrogate integer IDs only
where performance/partitioning justifies it.
 Store UTC timestamps; convert to user timezone at presentation boundaries.
 Use `numeric`/decimal-safe types for prices and monetary values where precision matters; never use binary
float for stored money.
 Partition high-volume candle/event tables by time and possibly provider/instrument when scale requires it.
 Use unique constraints to prevent duplicate provider candle ingestion.
 Use append-only event tables for setup/decision state changes and audits.
 Vector indexes are created only after representative corpus size and recall/latency benchmarking.

Appendix D - Final Principle
The project should not be built as “an LLM that looks at a chart and says buy or sell.” It should be built as a
private evidence system: trusted strategy knowledge + normalized market data + deterministic feature/rule
engines + risk veto + historical backtesting + a trained decision model + an LLM that explains and interacts. That
architecture is slower to build than a demo, but it is testable, auditable and capable of improving over time
without losing the original strategy discipline.
