Figure 2 - Runtime agent collaboration
The orchestrator does not mean eight separate models. Agents are logical roles with separate policies and tool
sets. One text model and one VLM can serve multiple agents; some deployments may use a single multimodal
model. This design reduces GPU cost while retaining role separation at the application layer.

6. Deployment Architecture
Figure 3 - Physical deployment topology
6.1 Baseline Single-Server Production
 One Linux GPU server runs reverse proxy, API, workers, LLM/VLM inference, Redis and optionally
PostgreSQL for minimal cost.
 Only 443 (and optionally 22 restricted to VPN/admin IP) is exposed publicly.
 Inference, PostgreSQL and Redis bind private/loopback interfaces.
 Nightly encrypted backups copy database/object metadata to separate physical/provider storage.
 Systemd or Docker restart policies recover failed containers.

9. Security Architecture
The most important architectural security decision is that the model never owns broad infrastructure
permissions. Tools are implemented server-side and exposed as narrow functions. A prompt can request a tool,
but authorization, validation and side effects are controlled by deterministic application code.
Control Plane Mechanism
Identity Local accounts, MFA, Telegram link challenges, scoped service
identities.
Authorization RBAC + explicit capability checks at API and tool invocation
layers.
Model Tooling Allowlisted tools with typed schemas; no arbitrary shell, SQL or
URL fetch from model.
Secrets Injected at runtime; per-provider read-only keys where
possible; never sent to LLM.
Network Private DB/inference ports; firewall; optional
WireGuard/Tailscale admin plane.
Audit Append-only event stream for auth, strategy publishing, configs,
signal changes and admin actions.
Supply Chain Pinned dependencies/images, vulnerability scanning, minimal
containers.
Backups Encrypted and periodically restore-tested.

Appendix C - Detailed Deployment Scenarios
C.1 Developer Laptop/Workstation
Docker Compose runs API, PostgreSQL, Redis, local object store and optional Ollama/llama.cpp. Market provider
uses read-only credentials. Telegram webhook may use tunnel only for development. No production secrets
reused.
C.2 Single GPU VPS/Bare Metal
Reverse proxy on host; all other containers private. GPU assigned only to inference containers. PostgreSQL
volume on reliable SSD. Backup agent writes encrypted snapshots off-host. Suitable for one user/low scan
volume.
C.3 Split App + GPU + DB
Public app node handles API/webhooks. GPU node only accepts inference calls from app/worker subnet. DB node
accepts Postgres/Redis connections only from app/worker nodes. Enables independent scaling and stronger
blast-radius isolation.
C.4 High Availability Future
Two API replicas behind load balancer; managed/replicated PostgreSQL; Redis HA; two GPU workers; queue
broker; object storage redundancy. Signal state remains DB-authoritative to avoid split-brain.

Appendix G - Future Live Execution Isolation (Not Baseline)
If live order execution is ever added, it must be designed as a separate bounded context and deployment, not a
tool casually added to the existing Signal Agent. The minimum architecture should include separate broker
credentials, allowlisted instruments, max daily risk, max order size, explicit human approval mode, broker
sandbox certification, reconciliation loop, kill switch, independent audit, and preferably a separate
network/service identity. No current component should possess permissions that can place a live order.
