1. Database Principles
 PostgreSQL is the source of truth for identities, strategy versions, setups/signals, audit and journal state.
 pgvector stores embeddings for approved document chunks; vector rows record embedding model version.
 Raw PDFs/images are stored in private object storage; database stores immutable object key, checksum and
metadata.
 Prices and monetary values use NUMERIC/DECIMAL, not float.
 Timestamps are TIMESTAMPTZ and persisted in UTC.
 Historical referenced entities use soft-retire/versioning rather than destructive mutation.
 High-volume candles may be time-partitioned; setup/signal/audit tables retain long-term evidence.

7. Partitioning and Retention
Data Partition / Retention Recommendation
Candles Monthly partitions for 1m/high-volume data; larger timeframes
may remain unpartitioned initially. Retention based on backtest
need.
Audit Events Monthly/yearly partition optional; retain long-term (e.g., 2+
years) for traceability.
Agent Steps/Tool Calls Retain structured metadata 90-365 days; redact/limit full
prompts if sensitive.
Screenshots Configurable 30-180 days unless attached to journal/setup
evidence.
Raw Documents Retain approved versions while referenced; retired content
archived, not silently deleted.
Notifications Delivery attempts 90-180 days; logical signal history longer.

10. Data Lineage and Reproducibility
A setup must be reproducible to the practical extent possible. The persistence chain is: setup -> strategy_version
-> strategy_rules -> rule_evaluations -> evidence candle ids/features -> risk_assessment -> optional
agent_run/steps -> model/prompt ids -> signal -> notification -> paper/journal outcome. Backtests additionally pin
dataset fingerprint, code/engine version and resolution assumptions.
11. Backup, Restore and Migration
 Perform PostgreSQL logical or physical backups on a schedule aligned to RPO; encrypt before leaving host.
 Back up object-storage metadata and raw resources, or ensure bucket versioning/redundancy separately.
 Restore drills must validate referential integrity and sample document/screenshot retrieval.
 Use schema migration tooling (Alembic recommended for FastAPI/SQLAlchemy). Each deployment runs only
reviewed forward migrations.
 Large destructive changes use expand-and-contract: add new column/table, dual write/backfill, switch reads,
then remove old structure in later release.
 Vector-dimension/model changes create parallel embedding rows or new table/index until migration is
complete.
12. Privacy and Audit
 Avoid storing raw access tokens; store hashes or encrypted secrets as appropriate.
 Do not persist model prompts containing secrets; input summaries should be redacted.
 Audit metadata should capture identifiers and changed field names/old-new hashes rather than secret
values.
 User deletion, if ever required in a multi-user release, must preserve legally/operationally required
anonymized audit and referenced trading artifacts according to policy.
